# Architecture

## Processes and trust boundaries

`electron/main.ts` owns the Windows window, native pickers, custom protocol, last-library preference and a fixed set of IPC handlers. Requests must come from the main frame of the app's own `fieldkit://app/` origin. Zod validates IDs, recipes, metadata, export options and drop payloads. File selection happens in the main process; dropped File objects are converted to paths with `webUtils` in the preload. No general filesystem, shell, arbitrary IPC or external URL-opening capability is exposed.

`electron/preload.ts` exposes a small typed `window.fieldKit` API. The renderer has sandboxing, context isolation and web security enabled, Node integration disabled, no webviews and no popups. Navigations and permission requests are denied. CSP restricts code/media to local resources; the session blocks HTTP(S) requests. The app uses a custom protocol, not a privileged renderer `file://` page. Managed media requests validate relative path syntax and real paths, use a constrained filename pattern, and support HTTP-style byte ranges for seeking.

`electron/worker.ts` runs the library in a Node worker thread. Operations are serialized so a render/export/import cannot race a database mutation. A newer render cancels a superseded render; import/export cancellation terminates active child processes and checks between image stages/files. Main tracks worker availability on error and exit and rejects requests immediately when unavailable. Media child PIDs are tracked in main so worker failure can terminate them. Restart processing creates a worker and reopens the last library. Shutdown waits for cancellation and cleanup, with a ten-second deadline that terminates the worker and media children if acknowledgment never arrives. Database disposal and shutdown acknowledgment are exception-safe. sharp and FFmpeg use bounded native concurrency; process output, file sizes, dimensions, duration and processing time have explicit limits.

`src/main.tsx` provides the React shell, selection/filtering, collection management, dialogs and details form. `src/workbenches.tsx` owns session undo/redo, auto-saved recipes, debounced rendered previews, crop/trim controls and playback. The Three.js module is dynamically loaded only when its scene tab is open; rendering happens on texture load, resize or user interaction, not a perpetual animation loop. Context loss produces a 2D fallback.

`src/recipe-saves.ts` owns optimistic recipe drafts for the whole library session, independently of editor mounts. Draft identity and session-generation checks prevent late replies from overwriting newer state. Reopening an editor uses its latest draft; only recipe/prepared fields are reconciled by recipe callbacks. Pending or failed writes block export; failed drafts remain available for retry. Export and library switching flush writes before proceeding. Unsaved Details navigation is guarded separately. Neither unsaved drafts nor editor undo history survive process termination.

Normal window close and application quit first request a renderer decision through a validated request-ID handshake. `src/close-guard.tsx` waits for outstanding recipe writes, offers saving/discarding changed Details, retries failures and prevents silent loss of invalid controls. Save waiting has an eight-second recovery timeout; it never silently approves closing. An unresponsive renderer gets a native choice after three seconds. Once closing is approved, the worker cancels media jobs but drains previously accepted recipe, metadata, collection, favorite, batch and preset writes before closing SQLite. The existing ten-second worker deadline remains a last resort. These guards cover normal application close, not forced termination or Windows logout/shutdown; see the [Electron lifecycle documentation](https://www.electronjs.org/docs/latest/api/app#event-before-quit).

`src/details.tsx` reconciles the saved canonical name/tags into its form, prevents duplicate submissions while writing, and exposes the same save operation to the close guard. Shared dialogs use the latest close callback so Escape cannot bypass a currently busy save. Validation errors appear inside the relevant form/dialog.

## Persistence

Each library has a versioned marker, SQLite database, byte-preserved originals and derived media. SQLite is Electron's built-in `node:sqlite`, with WAL and checkpoint-on-close. Assets have a unique SHA-256 and UUID. The asset record contains tags, notes, collection IDs, technical properties, recipe, relative original/thumbnail paths and sample-derived waveform. Collections have stable UUIDs and names. Display names never determine managed source paths.

Opening a library validates a candidate connection, schema version, integrity and records before replacing the active root/database. A failed candidate is disposed without closing the active library; a missing database is never silently recreated for an existing library.

Import copies to `.tmp` and inspects/generates derivatives there before moving validated files into managed folders and inserting their row. Exact duplicates can join the selected collection without creating a second asset. Failed jobs clean staged files; reopening cleans interrupted staging. sharp's file cache is disabled to avoid retaining Windows handles during these renames. Filesystem moves and SQLite insertion are not one crash-atomic transaction. Recipe and metadata writes are independent atomic SQLite statements. Saved recipes survive restart; session undo history does not.

Render caches are keyed by original hash, validated recipe and pipeline version (`renderer-v4`). Sidecars use a strict versioned schema and record SHA-256, byte count and measured format properties. Cache reads verify those properties and the media digest; bad or missing derivatives regenerate from originals. Sidecars are staged and renamed atomically, and cannot override the computed managed path. This detects accidental cache corruption, not a malicious library whose content and digest were both forged. The same render method supplies workbench previews, scene media and exports. Up to eight results per asset are retained. Library references never include the initial import path; relocating the entire closed library requires only selecting its new folder.

## Organization, presets and backups

Favorites, presets and Trash use additive SQLite tables. Core asset JSON and user_version remain v1, so older releases can still read asset records. On opening, core records and any existing extension records validate before the active library is replaced. Missing tables are created transactionally. Favorites and Trash timestamps are joined into renderer state and stripped from core JSON writes. Batch add/remove operations use a single SQLite transaction; missing IDs, invalid memberships or per-asset tag/collection limits roll back every change.

Trash stores only a validated asset ID and timestamp in `trashed_assets`. Moving and restoring a batch are atomic SQLite transactions, with no original/cache file deletion or movement. Repeated moves preserve the initial timestamp; repeated restores are harmless. The state snapshot includes every asset so backups retain Trash, while the renderer explicitly separates the active catalog from Trash. Backend asset access rejects stale edit, render, organization, favorite and export requests for trashed materials. Duplicate imports count matching originals in Trash without restoring them or modifying memberships. A failed candidate Trash record cannot replace the active library. Older releases ignore this table and show every asset; use 1.2 or newer for Trash behavior.

The renderer saves valid recipe drafts and Details before a move, then drops only the moved assets' editing drafts and scene references. Confirmation, Undo, single/batch restoration and read-only original previews use the narrow validated IPC bridge. Normal close waits for an in-flight Trash operation; the worker drains accepted move/restore writes during shutdown. Files remain on disk indefinitely: Trash is not a space-reclamation feature or the Windows Recycle Bin.

Presets store validated processing settings only. They never carry a source file, crop, orientation, trim or private notes. Audio fades scale together if necessary, and crossfade clamps to one third of the current trim. Presets have a library-wide cap of 500 and case-insensitive unique names within each type. The renderer applies them through the same undo/save/render path as ordinary controls. A tiny validation tolerance handles decimal subtraction at the 20 ms selection boundary; a processed loop may be shorter than the imported-recording minimum after overlap.

Backup is a serialized worker job. Main supplies the native-picker destination and the renderer flushes recipes and dirty Details first. The worker uses [Node SQLite's online backup API](https://nodejs.org/api/sqlite.html#sqlitebackupsourceDb-path-options) to snapshot the database, reads the snapshot's asset list, and streams originals/thumbnails into an exclusively created staging folder. Original SHA-256 values must match their stored import hashes; every copied file is hashed again. Managed paths are validated and realpath-contained. Preview caches and import staging are excluded. After successful verification, a fresh marker and empty cache/temp directories make the copy reopenable; the sibling folder is renamed to a unique dated destination. Backup never overwrites the active library or an existing backup. Normal cancellation/failure removes only this job's staging folder. Forced termination or power loss may leave a clearly named .partial folder; it is not a completed backup. Files on a physically failed drive cannot be recovered by an in-place backup.

The comparison view loads the managed original and the same processed PNG used for export. It labels the full original versus the square result; it does not claim pixel-aligned comparison across different crops or orientation.

## Batch preparation and export profiles

Version 1.3 adds `batch_history`, `export_profiles` and `export_preferences` tables without changing core asset JSON or database user_version. Existing extension records validate before a candidate library replaces the active one. History records contain only before/after recipe and prepared-state snapshots, with validated asset references; renderer state receives summaries. The last ten batches are retained, each limited to 1,000 selected IDs. Profiles are limited to 100 per library. Backups copy these tables through the existing SQLite snapshot.

Batch preparation runs as a serialized, cancellable worker media job. It resolves matching texture/sound presets, skips unassigned types and unchanged prepared materials, and renders every changed recipe before opening the commit transaction. A single transaction verifies that the saved recipes still match the starting snapshots, writes all new recipes and records history. Cancellation or failure before commit leaves batch recipes and history unchanged; disposable caches and legacy-waveform refreshes can remain. Original files are never modified. The UI flushes recipe/Details drafts first and retains them when saving fails.

Undo/redo are atomic database writes. They compare each material's current recipe and prepared flag with the expected snapshot before replacing those fields. A later individual edit, missing material or Trash flag prevents the entire reversal. Current metadata, favorites and memberships are preserved. Accepted undo/redo and profile writes drain during shutdown; active/queued batch preparation cancels. The renderer forgets only completed batch targets' stale drafts, remounts their editor and clears their scene references. Preview callbacks cannot replace the scene with a result for an older recipe.

`src/export-plan.ts` is shared by the dialog and worker. It validates output settings, derives temporary recipes and produces case-insensitive collision-resolved filenames. Texture size, audio channels and normalization can override saved settings solely for this export; crop/orientation/trim and other processing stay as saved. Prefix, case, whitespace and serial-number rules pass through the same filename sanitization. The dialog pages the complete plan in groups of 20 files. The worker renders those recipes and records measured output properties in the existing schema-v1 manifest.

Profiles store user-chosen settings, names and optional credits locally. Create/update/delete use strict IPC schemas; no destination paths or arbitrary file access are accepted. The last profile ID is remembered only after a ZIP successfully finalizes, and deleting that profile clears its preference by foreign key. If saving the preference fails after publication, the completed ZIP is reported as successful with a warning. Earlier releases ignore these optional tables and can still read the saved material recipes.

## Image processing

sharp validates the image and normalizes camera orientation. Crop coordinates refer to this upright image. Separate raw-pixel stages make ordering explicit: orientation/color conversion, crop, quarter-turn rotation, flip, square cover resize, brightness/saturation/contrast, then edge blend. Cropping at each stage avoids stretching. Opposing pixel pairs in a 12% edge band are mixed toward their mean, with a quadratic falloff and user strength. At 100% the opposing outermost rows/columns are identical. This reduces seams but does not synthesize new material content. PNG output is sRGB with an ICC profile and no capture EXIF/GPS.

## Sound processing

FFprobe identifies actual streams and duration. Required formats are forced to their expected demuxers to avoid accepting playlists or remote media. Waveform version 2 takes the maximum absolute channel magnitude before making a single envelope, preventing opposite-phase stereo channels from cancelling in the overview. The decoded envelope is sampled at 8 kHz into 600 peaks with a bounded pipe buffer. Legacy original waveforms are regenerated and persisted when audio is rendered. An intentionally mono output still displays its actual mono result, including real cancellation. Processing uses `atrim`, `asetpts`, `aresample`, `aformat`, `volume`, `afade`, and (for looping) split/trim/acrossfade/concat. Crossfade returns the middle followed by tail blended into head; duration is selection duration minus crossfade duration.

Float output preserves headroom until the final pass. The worker measures sample peaks, applies optional linear gain for −1 dBFS, rounds/clamps into 16-bit PCM, and writes a minimal WAV header with no private metadata chunks. FFprobe measures the resulting WAV and the final sample peak is measured from the quantized data. Chromium plays that exact file. Native controls provide seeking; a separate waveform is generated from the rendered output.

## Export transaction

The worker snapshots selected saved asset records, renders each, constructs a minimal manifest from measured results and assigns safe names with case-insensitive numeric collision suffixes. Notes, absolute paths, hashes, original media and capture metadata are omitted. Author/attribution are optional user input only.

yazl streams a ZIP to a unique `.partial` sibling. After successful completion and a cancellation check, an atomic non-overwriting hard link creates the final ZIP. The temporary name is then removed. Unsupported filesystems fail safely with a local-NTFS instruction. Graceful cancellation/failure removes the partial. A machine crash/power loss can leave a hidden `.partial` file, but never an apparently completed final pack. Existing exports are never silently overwritten.

Version 1.4 shares preparation, naming and measured manifest generation between ZIP and folder export. `electron/export-pack.ts` handles publication. Folder names use a strict single-segment Windows-name schema; the main process owns the parent-folder picker. The worker resolves the parent's real path and rejects destinations inside the managed library, including junction aliases. It copies files into an exclusively created sibling staging directory, checks cancellation during streamed copies and metadata writes, then uses Windows directory rename. Windows refuses even an empty existing destination, so a racing directory is never replaced. Only this job's staging path is eligible for cleanup. Non-Windows folder publication is explicitly unsupported; no copy/merge fallback is used.

`export_history` is an additive table with at most twenty successful pack snapshots. Each stores ordered IDs and original hashes, recipe/name/tag snapshots, export settings, credits, format, timestamp and destination basename. It contains no original media or destination directories. Library state exposes compact summaries; a UUID-validated read retrieves a full record for review. Re-export resolves current managed originals, refuses Trash/missing/hash-changed material, then renders the recorded recipe without writing it to the asset. Hash validation occurs even when a processed cache entry is available. Profiles may change or be deleted without invalidating a snapshot. The renderer saves valid current recipes and Details before opening an export, reconciles history separately from editable assets, and lets users choose a new format/destination.

History and last-profile preference are bookkeeping after successful filesystem publication. A failed database write yields a completed-pack warning rather than reporting a nonexistent export failure. History insertion/pruning are one transaction. Reopening validates all history records before switching libraries; backups carry the table through the normal SQLite snapshot. Export/close cancellation uses the existing serialized worker protocol.

## Dependencies and references

Electron 44.4.5, React 19.3.0, TypeScript 7.0.2, sharp 0.35.4, Three.js 0.186.1, Vite 8.3.1, electron-builder 26.15.3, and BtbN FFmpeg n8.1.3-20260925. Godot's importer defaults explicitly select PCM without extra trimming, normalization or resampling; the test compares decoded texture pixels and raw PCM samples with the exports. Headless import, a rendered Windows/OpenGL scene and dummy-driver loop timing are separately recorded. This does not verify physical speakers or other engines.
